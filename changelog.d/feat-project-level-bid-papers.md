### Four GCs invite you to the same job: the supplier quotes, addenda and spec sections are now the JOB's, so every GC's row shows them (Cyrus)
`feat/project-level-bid-papers`

Before this, a supplier quote or an addendum filed under GC A's invitation was invisible on GC B's row for the same building, because each paper hung off the ONE invitation it was filed under (the design's "P1b", the not-done item of `feat/bid-project`). An estimator with four GCs on one hospital filed the same framing quote four times or looked at one row and thought the others had nothing.

**Heads-up for Slack before the push: this adds a migration** (`20261026120000_bid_papers_on_project`). Additive only: three nullable `bidProjectId` columns (on `BidQuote`, `BidAddendum`, `BidSpecSection`), one new table (`BidAddendumAcknowledgement`), their indexes and foreign keys (SET NULL on the project links, CASCADE on the new table), and an idempotent backfill. Nothing dropped, renamed or tightened, so the build still serving while it applies is unaffected. Generated with `prisma migrate diff --from-schema-datamodel <copy of HEAD> --to-schema-datamodel prisma/schema --script` (no database, no shadow database); the backfill was added by hand. No new `jobId` or `companyId`, so `HANDLED_MODELS` and the cleanup scripts are unchanged (the new table cascades from the addendum and the invitation, both of which already clean up).

**The design, and why it is the least risky one.** Each paper gets a nullable `bidProjectId`, backfilled from the invitation it was filed under, and the invitation link STAYS, now meaning "filed under" (who it came in with). Reads gather by project and fall back to the filing invitation only where `bidProjectId` is null. Two alternatives were rejected: replacing the invitation link with the project link is a drop-and-add of a column the running build reads (the #378 outage shape), and a separate "filing" table is a second place to keep right for no gain. The one place that decides which papers an invitation sees is `lib/estimating/bid-papers.ts` (`paperWhere`, `paperWhereMany`, `papersFor`, `paperWhereForJob`), and the invariant every write keeps is that a paper's project equals its filing invitation's project. Nullable-and-SET-NULL means a paper written by the old build during a deploy is not lost: it is read through its filing invitation and healed at the next merge.

**What is the project's, and what stays per GC (the decision).**
- Project's: the quote (about the building), the addendum DOCUMENT and its readings and per-scope decisions (the building's drawings changed), the spec section and its readings.
- Per GC, deliberately: the addendum ACKNOWLEDGEMENT. Each GC's bid form demands its own, and a project-wide date would tell GC B's row its form was in order because GC A's was; that is the most common reason a complying bid is thrown out. So `BidAddendum.acknowledgedOn` keeps meaning "acknowledged on the filing invitation's form" (no data movement), and every other GC's is a `BidAddendumAcknowledgement` row. No row is "not acknowledged on that form". `acknowledgedOnFor` is the one function that reads the pair, and `acknowledgeBidAddendum` now takes the invitation the row is shown on (a page loaded before this ships omits it and means the filing one).
- Per GC and unchanged: bid-form requirements (`BidRequirement`), the lines (alternates, unit prices, allowances), the price adjustment, decline and outcome, status and the send record.
- Carried quote: one per package PER PROJECT now (carrying Beta on GC B's row un-carries Alpha on GC A's), and "Add to estimate" puts it on the project's one estimate, whichever GC's row it is pressed from.

**Merge, split, delete.**
- Merge: the papers follow into the surviving project. If the same addendum was filed separately under each GC before merging, the merged project shows it twice; nothing is auto-deduplicated, because two same-named addenda may be different documents. Delete one by hand (and read the acknowledgement on each row first).
- Split: the papers STAY WITH THE PROJECT. What the split-off GC keeps is only what is genuinely its own (the list above), including its acknowledgement of each addendum, which is kept as a row so merging it back restores it. A paper that was filed under it is re-filed onto the project's oldest remaining invitation, so "came in with ..." reads that GC from then on. Chosen over "the papers go with the GC they were filed under" because filing under one invitation was never a statement that the paper is about a different building, and over leaving the filing link dangling because deleting the split-off GC would then cascade away papers its former siblings still show.
- Delete an invitation: what was filed under it moves to a sibling first, in the same transaction, instead of cascading away from the other GCs' rows. A project's only invitation still takes its papers with it, as before. Acknowledgements follow: the sibling's own becomes the column value.

**On screen.** `/bids` (and C Stream Bid's `/bid/bids`, which renders the same component) shows the project's quotes, addenda and spec sections on every GC's row, with "came in with <GC>'s invite" where a paper was filed under another GC's invitation. An addendum's "acknowledged / not acknowledged" is that row's GC's. The delete tooltips say a paper belongs to the whole job. The job-side readers (proposal facts, takeoff currency, estimate cross-checks), the estimate-check and workspace agents, Ask's levelling and compliance answers, and "Send quote request" (which attaches the project's spec sections and addenda) all read by project now. The export carries `bidProjectId` and has a file for the other GCs' acknowledgements.

Not done: the bid watcher still raises one "addendum not looked at" per addendum (against the invitation it was filed under, and only while that invitation is still INVITED); a per-GC version would repeat the same finding on every row. Nothing deduplicates after a merge (above). `BidRequirement` stays per invitation and was not examined for a project-level "everyone needs the bid bond" version.

The specific check: `pnpm exec vitest run --config vitest.db.config.mts lib/estimating/bid-papers.dbtest.ts` runs the migration's own backfill SQL on seeded pre-migration rows twice (the second run updates zero rows and no already-set project is overwritten), then a quote filed under GC A on GC B's row (edit and carry from B), a carried quote and a priced-scope addendum filed under GC B reaching the job linked through GC A, per-GC acknowledgement (including the refusals for an invitation on another project or another company), merge, split (and merge back), and delete, against real rows. `e2e/specs/bid-desk.spec.ts` step 9 walks it in a browser and has not been run.
